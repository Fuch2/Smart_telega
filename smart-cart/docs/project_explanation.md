# SmartCart — Полное объяснение проекта

> Этот документ написан так, чтобы человек без знания программирования мог объяснить любой файл проекта инвесторам, партнёрам или команде.

---

## Что это такое и зачем

**SmartCart** — это программно-аппаратная система управления умной тележкой на производстве. Тележка используется для подбора и выдачи катушек с материалами (например, SMD-компонентами для монтажа плат) на производственную линию.

### Проблема, которую решает система

На производстве оператор должен взять десятки катушек с компонентами из склада и разложить их по нужным слотам. Без автоматизации это делается вручную по бумажным спискам — долго и с ошибками. SmartCart:

- **Показывает оператору, куда именно положить каждую катушку** (LED-подсветка нужного слота)
- **Подтверждает, что катушка положена в правильное место** (физический датчик-переключатель)
- **Ведёт полную историю** что, куда и когда было положено
- **Не даёт перепутать** — при неправильном слоте система фиксирует ошибку

## Из чего состоит система

Система состоит из **четырёх компонентов**, которые работают вместе:

```
┌─────────────────────────────────────────────────────────────┐
│  Raspberry Pi (одноплатный компьютер внутри тележки)        │
│                                                             │
│  ┌─────────────┐  ┌──────────────┐  ┌──────────────────┐   │
│  │   Qt UI     │  │   Web API    │  │  CLI-утилита     │   │
│  │  (экран)    │  │  (браузер)   │  │  (диагностика)   │   │
│  └──────┬──────┘  └──────┬───────┘  └────────┬─────────┘   │
│         └────────────────┼───────────────────┘             │
│                   ┌──────┴──────┐                          │
│                   │  Бизнес-    │                          │
│                   │  логика     │                          │
│                   └──────┬──────┘                          │
│                   ┌──────┴──────┐                          │
│                   │  SQLite БД  │                          │
│                   └─────────────┘                          │
└──────────────────────────┬──────────────────────────────────┘
                           │ UART (последовательный порт)
                           │
               ┌───────────┴───────────┐
               │  STM32 (микроконтроллер на плате тележки)  │
               │  - Управляет LED-лентой (подсветка слотов) │
               │  - Читает переключатели (датчики слотов)   │
               └───────────────────────────────────────────┘
                           +
               ┌───────────────────────┐
               │  RFID-считыватели     │
               │  (идентификация модулей) │
               └───────────────────────┘
                           +
               ┌───────────────────────┐
               │  Сканер штрихкодов    │
               │  (ввод артикула катушки) │
               └───────────────────────┘
```

## Технологический стек и почему именно он

| Технология | Зачем выбрана |
|---|---|
| **C++17/20** | Основной язык. Выбран за скорость работы и прямой доступ к железу (UART, SPI, GPIO). Python был бы медленнее и хуже работал бы с аппаратными интерфейсами в реальном времени. |
| **Qt 5/6** | Графический интерфейс. Индустриальный стандарт для встраиваемых экранов. Работает на Raspberry Pi без браузера. Содержит готовые виджеты, систему сигналов между компонентами и поддержку многопоточности. |
| **SQLite** | База данных. Работает без сервера — просто файл на диске. Идеально для одной тележки: надёжна, не требует обслуживания, переживает внезапное отключение питания. |
| **CMake** | Система сборки. Стандарт индустрии для C++ проектов. Позволяет собрать проект одной командой на любой машине. |
| **spdlog** | Библиотека логирования. Быстро пишет логи в файл без блокировок. Нужна чтобы видеть историю работы системы при диагностике. |
| **nlohmann/json** | Чтение JSON-файлов (конфигурация, заказы). Самая популярная C++ библиотека для JSON: простой синтаксис, не требует настройки. |
| **Python + Flask** | Веб-интерфейс для мониторинга (второй экран или телефон технолога). Python выбран специально — добавить простой веб-страницу на C++ было бы в 10 раз сложнее. |
| **GoogleTest** | Автоматические тесты. Проверяют, что бизнес-логика работает правильно без подключения реального железа. |

## Структура папок и что где лежит

```
smart-cart/
├── apps/
│   └── smartcart_app/        ← точки входа в программу (main файлы)
├── src/
│   ├── domain/               ← бизнес-логика (что такое катушка, слот, заказ)
│   ├── application/          ← сервисы (как выполнять операции)
│   ├── infrastructure/       ← "железо" и база данных
│   └── presentation/         ← интерфейс пользователя (экран)
├── config/                   ← файлы настройки
├── docs/                     ← документация
├── tests/                    ← автоматические тесты
└── tools/                    ← вспомогательные утилиты
```

### Принцип "луковицы" (Clean Architecture)

Код построен по принципу слоёв. Внутренние слои **ничего не знают** о внешних:

```
      domain        ← знает только о бизнес-понятиях
        ↑
   application      ← знает о domain, не знает о железе
        ↑
  infrastructure    ← работает с железом, БД, файлами
        ↑
   presentation     ← рисует экран
```

**Зачем это нужно:** если завтра SQLite заменить на PostgreSQL — надо поменять только один файл в `infrastructure`, весь остальной код остаётся нетронутым. Аналогично с железом: можно подключить другой сканер штрихкодов — меняется только один драйвер.

## Подробный разбор каждой папки

---

### `apps/smartcart_app/` — Точки входа в программу

#### `main_qt.cpp` — Запуск с графическим интерфейсом
Это **стартовая точка** программы с экраном. Когда оператор включает тележку, операционная система запускает именно этот файл.

Что он делает:
1. Создаёт `QApplication` — Qt-объект, который управляет всей программой и экраном
2. Создаёт `AppBootstrap` — "строитель", который собирает все части системы вместе
3. Вызывает `bootstrap.launch()` — система начинает работу
4. `app.exec()` — программа "зависает" в цикле ожидания нажатий и событий до выключения

**Библиотека QApplication** — это фундамент любого Qt-приложения. Без неё кнопки, экраны и события не работают.

#### `main.cpp` — Запуск без экрана (CLI)
Это **консольная версия** для технического персонала. Запускается из командной строки для диагностики и управления без экрана.

Поддерживает команды:
- `--diag` — показать состояние системы и железа
- `--import-order FILE` — загрузить новый заказ из файла
- `--workflow-next` — перевести заказ на следующий этап
- `--issue BARCODE` — отметить материал как выданный на линию
- `--return-leftover BARCODE` — вернуть остаток на склад
- `--rfid-watch` — мониторинг RFID в реальном времени
- `--rfid-probe` — тестирование RFID-считывателей

**Зачем нужен CLI:** позволяет управлять системой по SSH без физического доступа к тележке. Удобно для тестирования и производственной поддержки.

#### `AppBootstrap.hpp / AppBootstrap.cpp` — "Строитель" всей системы
Этот файл — **главный конструктор**. Он собирает все части системы вместе как конструктор Lego.

Что делает `AppBootstrap`:
1. Читает `config.json` — узнаёт настройки (какой порт UART, включён ли RFID и т.д.)
2. Открывает базу данных SQLite, запускает миграции схемы
3. Создаёт все репозитории (слои работы с БД)
4. Создаёт все сервисы (бизнес-логику)
5. Подключается к STM32 через UART
6. Запускает RFID-считыватели если они включены
7. Создаёт Qt-окна и связывает их с сервисами
8. Обрабатывает переключение RFID-модулей (когда тележку "привязывают" к новому модулю)

Принцип здесь — **Dependency Injection (DI)**: каждый сервис не создаёт свои зависимости сам, а получает их от `AppBootstrap`. Это делает тестирование простым — в тестах вместо реального железа подставляются заглушки (Mock).

### `src/domain/` — Бизнес-логика (самый важный слой)

Этот слой описывает **предметную область** — что такое катушка, слот, заказ, операция. Здесь нет ни базы данных, ни железа, ни экрана. Только чистые понятия производственного процесса.

#### `entities/ReelRecord.hpp` — Катушка
Описывает одну **катушку с материалом**:
- `barcode` — штрихкод катушки (уникальный идентификатор)
- `moduleId` — к какому модулю тележки относится
- `slotIndex` — в каком слоте лежит (номер ячейки)
- `placedAt` — когда положили
- `removedAt` — когда вынули (если вынули)

Хранит **историю движения катушки**: система знает, что катушка с артикулом "XYZ123" была положена в слот 5 в 14:30 и вынута в 15:45.

#### `entities/Slot.hpp` — Слот (ячейка тележки)
Описывает одну **ячейку** в тележке:
- `moduleId` — к какому модулю относится
- `slotIndex` — номер ячейки
- `ledIndex` — какой светодиод её подсвечивает
- `state` — состояние:
  - `Free` — пустая, можно класть
  - `Occupied` — занята, катушка лежит
  - `Reserved` — зарезервирована (ждём пока положат)
  - `Error` — ошибка (физически занята, но в БД пусто или наоборот)

#### `entities/CartWorkflow.hpp` — Состояние заказа
Описывает **в каком этапе** сейчас находится тележка. Это как статус посылки на Почте России, только для производственного процесса:

```
FREE → ORDER_LOADED → PICKING_MATERIALS → LOADING_FEEDERS →
FEEDER_PREP → ISSUING_TO_LINE → ORDER_COMPLETED →
INSPECTING_LEFTOVERS → RETURNING_LEFTOVERS → FREE
```

Каждый этап означает конкретное действие:
- `FREE` — тележка свободна, нет активного заказа
- `ORDER_LOADED` — заказ загружен, ждём начала подбора
- `PICKING_MATERIALS` — оператор сканирует катушки и кладёт в слоты
- `LOADING_FEEDERS` — катушки загружаются в питатели станка
- `FEEDER_PREP` — подготовка питателей
- `ISSUING_TO_LINE` — выдача материалов на линию
- `ORDER_COMPLETED` — заказ выполнен
- `INSPECTING_LEFTOVERS` — проверка остатков
- `RETURNING_LEFTOVERS` — возврат остатков на склад

Также описывает статусы позиций заказа (`OrderItemStatus`):
- `Pending` — ещё не положено
- `Placed` — положено в слот
- `Issued` — выдано на линию
- `Returned` — возвращено на склад
- `Missing` — не найдено
- `WrongSlot` — положено не в тот слот

#### `entities/Operation.hpp` — Операция
Фиксирует **одно конкретное действие** оператора:
- `type` — тип: добавление катушки, замена, удаление
- `status` — статус: в процессе, выполнена, отменена, ошибка
- `barcode`, `slotIndex` — что именно делалось
- Временные метки начала и завершения

#### `entities/ModuleInfo.hpp` — Модуль
Описывает **аппаратный модуль** тележки (физический блок со слотами):
- `status` — Online/Offline/Maintenance
- `kind` — тип: REEL (для катушек) или FEEDER (для питателей станка)
- `slotCount` — количество слотов в модуле

#### `errors/ErrorCode.hpp` — Коды ошибок
Перечень **всех возможных ошибок** системы в одном месте:
- `InvalidBarcode` — неправильный штрихкод
- `SlotOccupied` — слот уже занят
- `NoFreeSlot` — нет свободных слотов
- `ReelNotFound` — катушка не найдена в базе
- `WrongSlotInteraction` — положено не в тот слот
- `Stm32CommunicationError` — нет связи с микроконтроллером
- `PersistenceError` — ошибка базы данных
- И другие...

#### `services/SlotStatePolicy.hpp` — Правила переходов состояний слота
Описывает **бизнес-правила**: когда можно что делать со слотом.
- `canPlace(slot)` — можно ли положить катушку (только если Free или Reserved)
- `canRemove(slot)` — можно ли убрать катушку (только если Occupied)
- `canReplace(slot)` — можно ли заменить (только если Occupied)

Эти правила **в одном месте**, поэтому при изменении логики не надо искать по всему коду.

#### `services/LedMappingPolicy.hpp` — Маппинг слотов на светодиоды
Описывает **соответствие**: слот №5 → светодиод №9. Это нужно потому что физическое расположение LED на ленте не всегда совпадает с нумерацией слотов. Логика маппинга вынесена в отдельный объект, чтобы легко менять под разные конфигурации тележки.

### `src/application/` — Сервисы (координация процессов)

Этот слой **не знает** ни о базе данных, ни о железе напрямую. Он работает через **интерфейсы (порты)** — контракты на то, что нужно сделать. Реальные реализации подставляются снаружи.

#### `ports/` — Интерфейсы (контракты)

Это **описания обязательств**: "кто бы ни реализовывал работу с базой данных, он обязан уметь делать вот это".

- **`IReelRepository.hpp`** — контракт для работы с катушками в БД: добавить, найти по штрихкоду, пометить убранной, получить состояние слотов
- **`IOrderRepository.hpp`** — контракт для работы с заказами: создать заказ, добавить позицию, найти по штрихкоду, обновить статус
- **`IWorkflowRepository.hpp`** — контракт для хранения состояния заказа: получить текущее состояние, установить новое
- **`IOperationRepository.hpp`** — контракт для истории операций: добавить операцию, обновить её статус
- **`IModuleRepository.hpp`** — контракт для работы с модулями: добавить, обновить статус
- **`IStm32Link.hpp`** — контракт для связи с микроконтроллером: открыть соединение, отправить команду, получить ответ, подписаться на события
- **`IRfidProvider.hpp`** — контракт для RFID: считать метку, подписаться на появление новой
- **`IScannerProvider.hpp`** — контракт для сканера штрихкодов: подписаться на сканирование
- **`IEventLogger.hpp`** — контракт для логирования: записать событие с уровнем, кодом и текстом
- **`IDiagnosticsRepository.hpp`** — контракт для диагностики: получить последние события

**Зачем нужны интерфейсы:** в тестах вместо реального STM32 подключается `MockStm32Link` — заглушка, которая отвечает заранее заданными ответами. Бизнес-логика тестируется полностью без реального железа.

#### `dto/` — Объекты передачи данных

**`Commands.hpp`** — структуры для команд от UI к бизнес-логике:
- `AddReelCommand` — добавить катушку: штрихкод + (опционально) предпочтительный слот
- `ReplaceReelCommand` — заменить катушку: штрихкод новой
- `RemoveReelCommand` — убрать катушку: модуль + слот

**`Events.hpp`** — структуры для событий из бизнес-логики в UI:
- `SlotPhysicalChangedEvent` — физически изменился слот (нажат/отпущен переключатель)
- `OperationFinishedEvent` — операция завершена (успешно или нет)
- `SlotsSnapshotEvent` — текущее состояние всех слотов

**`HardwareStatus.hpp`** — статус железа для отображения на экране:
- Статус STM32: онлайн/оффлайн, последняя связь, последняя ошибка
- Статус RFID: онлайн/оффлайн, последняя связь, последняя ошибка
- Метод `isHealthy()` — все ли системы в норме
- Метод `summary()` — текстовая сводка для экрана

#### `services/WorkflowService.hpp / .cpp` — Управление жизненным циклом заказа

**Главный оркестратор** всего производственного процесса. Знает, в каком состоянии находится заказ и что можно делать дальше.

Ключевые методы:

| Метод | Что делает |
|---|---|
| `startFeederLoading()` | Переводит из PICKING_MATERIALS → LOADING_FEEDERS |
| `completeFeederLoading()` | Переводит из LOADING_FEEDERS → FEEDER_PREP |
| `notifyMaterialPlaced()` | Уведомляет о размещении материала, проверяет все ли положено |
| `startIssuingToLine()` | Начало выдачи на линию → ISSUING_TO_LINE |
| `markItemIssued(barcode)` | Отмечает конкретный материал как выданный |
| `completeIssuing()` | Завершает выдачу → ORDER_COMPLETED |
| `markLeftoverReturnedByBarcode()` | Возврат остатка по штрихкоду |
| `generateOrderReport()` | Формирует отчёт: сколько выдано, сколько осталось |

Сервис читает текущее состояние из `IWorkflowRepository` и записывает новое. Ничего не знает о базе данных — только вызывает методы интерфейса.

#### `services/StartupService.hpp / .cpp` — Инициализация при запуске

Выполняется **один раз при запуске**. Задача: убедиться, что состояние в базе данных соответствует реальному физическому состоянию слотов.

Шаги:
1. Проверяет, есть ли запись о модуле в БД — если нет, создаёт
2. Инициализирует все слоты как "свободные" если они не существуют
3. Пингует STM32 — проверяет связь
4. Ждёт сигнал "STM32 готов" (до таймаута)
5. Запрашивает у STM32 текущее состояние всех переключателей (snapshot)
6. **Согласует** физическое состояние и состояние в БД:
   - Физически занят + в БД запись есть → **Occupied** (всё хорошо)
   - Физически пусто + в БД нет записи → **Free** (всё хорошо)
   - Физически занят + в БД нет записи → **Error** (катушка лежит, но мы не знаем какая)
   - Физически пусто + в БД есть запись → **Error** (в БД числится, но физически нет)

Это критически важно при **восстановлении после сбоя питания**: система не "теряет" катушки.

#### `services/RecoveryService.hpp / .cpp` — Восстановление незавершённых операций

Обрабатывает **незавершённые операции** после перезапуска. Например, если электричество отключилось в момент когда оператор клал катушку.

Для каждой незавершённой операции:
- **Добавление катушки**: проверяет физически — лежит ли катушка? Если да → отмечает операцию выполненной. Если нет → отменяет.
- **Замена катушки**: аналогичная логика с проверкой нового физического состояния
- **Удаление**: проверяет что слот физически пуст

#### `services/AddReelService.hpp / .cpp` — Добавление катушки в слот

Управляет **процессом добавления** одной катушки:

1. Проверяет штрихкод (не пустой, не длиннее 64 символов)
2. Ищет свободный слот в БД
3. Резервирует слот (статус → Reserved)
4. Создаёт запись об операции в БД
5. Подсвечивает слот **зелёным** через STM32
6. Запускает фоновый поток ожидания:
   - Подписывается на события от STM32 (`EvtSwitchChanged`)
   - Ждёт нажатия переключателя в нужном слоте
   - При подтверждении: создаёт запись о катушке, статус → Occupied
   - При таймауте или отмене: освобождает слот, отменяет операцию
7. Гасит LED

Используются **shared_ptr** для `mutex` и `condition_variable` — это C++ механизм безопасного ожидания между потоками. `shared_ptr` гарантирует, что объекты синхронизации не уничтожатся пока фоновый поток ещё работает.

#### `services/ReplaceReelService.hpp / .cpp` — Замена катушки

Управляет заменой: старую убрать, новую положить.

1. Находит существующую катушку по штрихкоду в БД
2. Подсвечивает слот **красным** — сигнал "убери эту"
3. Ждёт когда переключатель отпустится (катушку убрали)
4. Подсвечивает слот **зелёным** — сигнал "положи новую"
5. Ждёт когда переключатель нажмётся (катушку положили)
6. Помечает старую катушку убранной, создаёт запись о новой

#### `services/Stm32PollingService.hpp / .cpp` — Опрос микроконтроллера

**Сердце взаимодействия с железом**. Фоновый поток, который каждые 500мс опрашивает STM32.

Что делает:
- Каждые 500мс запрашивает состояние всех переключателей (snapshot)
- Если STM32 недоступен — пытается переподключиться с нарастающей задержкой
- Обрабатывает входящие события (EvtSwitchChanged) — мгновенная реакция без ожидания
- **Дебаунсинг** (50мс): не реагирует на кратковременные дребезги контактов переключателя
- При физическом занятии слота:
  - Проверяет, есть ли pending scan (оператор только что сканировал штрихкод)
  - Если есть — связывает катушку с заказом
  - Если положили не в тот слот — фиксирует ошибку WrongSlotInteraction
- При физическом освобождении слота — помечает катушку убранной
- Обновляет статус здоровья оборудования

Метод `recordBarcodeScan(barcode)` — вызывается когда оператор сканирует штрихкод. Ищет его в текущем заказе и создаёт "ожидающий скан", который будет связан с физическим нажатием переключателя.

#### `services/SwitchEventHandler.hpp / .cpp` — Обработчик событий переключателей

Выделен из `Stm32PollingService` как отдельный класс, чтобы не перегружать основной сервис.

Отвечает за:
- Приём событий `EvtSwitchChanged` от STM32
- Обновление внутренних снапшотов (rawSnapshot и lastSnapshot)
- Вызов логирования

#### `services/RfidModuleMonitorService.hpp / .cpp` — Мониторинг RFID

Следит за RFID-модулем тележки. Каждые 500мс читает RFID.

Логика работы:
- Если считал ожидаемый UID → модуль в зоне → Online
- Если долго не видит ожидаемый UID (по умолчанию 3 секунды) → модуль ушёл → Offline
- Если считал **чужой** UID (другой модуль поднесли к тележке) → вызывает `switchCb_` — запрос на переключение на этот модуль

Это позволяет **одной тележке обслуживать несколько модулей**: подносишь другой модуль к считывателю — тележка автоматически переключается.

#### `services/OrderImportService.hpp / .cpp` — Загрузка заказа из JSON

Принимает JSON-файл заказа и создаёт записи в базе данных.

Формат заказа:
```json
{
  "order_id": "WO-2026-0042",
  "title": "Плата управления v3",
  "items": [
    { "barcode": "C0402X5R100NF", "quantity": 200 },
```

Что делает:
- Проверяет обязательные поля

- Обнаруживает **остатки предыдущего заказа** — катушки которые уже лежат в слотах и совпадают с новым заказом
- Переводит workflow в состояние `OrderLoaded`

#### `services/BomOrderImportService.hpp / .cpp` — Загрузка из XLSX (BOM)

Позволяет загружать заказ прямо из **Excel-файла BOM** (Bill of Materials — список компонентов для платы).

XLSX — это на самом деле ZIP-архив с XML-файлами внутри. Сервис:
1. Распаковывает XLSX через системную утилиту `unzip`

#### `services/AdminDiagnosticsService.hpp / .cpp` — Диагностика для администратора

- Возможность сброса тестовой тележки (очистка данных)

#### `services/ModuleSnapshotPollingService.hpp / .cpp` — Опрос snapshot модуля

Специализированный сервис для периодического опроса состояния слотов отдельного модуля. Работает параллельно с основным `Stm32PollingService` для независимого мониторинга.

#### `state/AppStateMachine.hpp / .cpp` — Конечный автомат приложения

Управляет **состоянием самого приложения** (не заказа, а именно программы):

```
Idle → Initializing → Ready → Operating → Error
```

- `Idle` — программа запустилась, ещё ничего не делает
- `Initializing` — выполняются `RecoveryService` и `StartupService`
- `Ready` — инициализация прошла успешно, ждём действий
- `Operating` — выполняется операция (добавление/замена катушки)
- `Error` — произошла критическая ошибка

Использует **Qt signals/slots** — механизм уведомлений в Qt. Сигналы — это "объявления о событии" (`stateChanged`, `operationFinished`, `errorOccurred`). Слоты — это методы, которые на них реагируют. Qt автоматически вызывает нужные методы UI когда что-то меняется в бизнес-логике.

Метод `scanBarcode(barcode)`:
1. Нормализует штрихкод (убирает пробелы)
2. Если активна операция в состоянии `Operating` → передаёт в текущую операцию
3. Определяет: это замена существующей катушки или добавление новой?
4. Запускает нужный сервис

#### `db/SqliteConnection.hpp / .cpp` — Соединение с базой данных

Оборачивает низкоуровневый SQLite C API в удобный класс.

**SQLite** — это встраиваемая база данных: весь движок БД компилируется прямо в программу, данные хранятся в одном файле. Не требует установки сервера баз данных. Выбрана потому что:
- Надёжна при внезапном отключении питания (WAL-mode — Write-Ahead Logging)
- Работает без сетевого соединения
- Нет администрирования
- Идеальна для одного устройства

Ключевые настройки:
- **WAL mode** — записи сначала идут в журнал, потом в основной файл. При сбое питания данные не теряются.
- **busy_timeout** — если другой процесс занял БД, ждёт до 5 секунд вместо немедленной ошибки
- **Транзакции** — группа операций выполняется "всё или ничего": либо все изменения сохранились, либо ни одно

Метод `runMigrations()` — **автоматическое обновление схемы БД**. При обновлении программы новые SQL-файлы из папки `migrations/` применяются автоматически, старые — пропускаются. Список применённых миграций хранится в таблице `schema_migrations`.

#### `hw/stm32/Protocol.hpp` — Протокол общения с микроконтроллером

Описывает **формат сообщений** между Raspberry Pi и STM32:

Структура одного фрейма:
```
[SOF1][SOF2][Ver][Type][Seq][CmdId][Len_Lo][Len_Hi][...Payload...][CRC_Lo][CRC_Hi]
```
- `SOF1/SOF2` — маркеры начала фрейма (0xAA 0x55), чтобы надёжно найти начало в потоке байт
- `Ver` — версия протокола (для обратной совместимости при обновлении прошивки)
- `Type` — тип: Cmd (команда), Resp (ответ), Ack, Nack, Evt (событие)
- `Seq` — порядковый номер (чтобы связать команду с ответом)
- `CmdId` — код команды (Ping, GetSwitchSnapshot, LedSetSlot, и т.д.)
- `Payload` — данные (до 512 байт)
- `CRC` — контрольная сумма (защита от битых данных на UART)

Команды (`CommandId`):
- `Ping` — проверка связи
- `GetReadyState` — STM32 готов?
- `GetSwitchSnapshot` — дай состояние всех переключателей
- `LedSetSlot` — установи цвет LED для слота
- `LedApply` — примени изменения LED
- `LedClearAll` — погаси все LED
- `EvtSwitchChanged` — событие: переключатель изменился (из STM32 в Pi)
- `EvtReady` — событие: STM32 загрузился и готов

#### `hw/stm32/FrameCodec.hpp / .cpp` — Кодировщик/декодировщик фреймов

Преобразует структуру `Frame` в массив байт для отправки (encode) и обратно (decode).

**CRC16-CCITT** — алгоритм контрольной суммы. Каждый фрейм "подписывается" двумя байтами. На принимающей стороне сумма пересчитывается и сравнивается. Если данные повредились при передаче — несовпадение суммы обнаружит ошибку.

**StreamParser** — потоковый парсер. UART передаёт байты непрерывным потоком. Парсер читает по одному байту и ищет начало фрейма, потом накапливает байты хедера, потом payload, потом CRC. Это классический **конечный автомат** (state machine):

```
WaitSof1 → WaitSof2 → Header → Payload → CrcLo → CrcHi → (готово, сброс)
```

Счётчики `parse_error_count_` и `crc_drop_count_` — для диагностики качества соединения.

#### `hw/stm32/UartStm32Link.hpp / .cpp` — UART-соединение со STM32

Реализует интерфейс `IStm32Link`. **Реальная** работа с последовательным портом.

**UART** (Universal Asynchronous Receiver-Transmitter) — простой протокол передачи данных по проводу. Raspberry Pi и STM32 соединены физически двумя проводами: TX (передача) и RX (приём). Скорость — 115200 бит/сек.

Архитектура:
- **`rxThread_`** — отдельный поток, который непрерывно читает байты из UART и передаёт в `StreamParser`
- **`sendCommand()`** — синхронный вызов: отправляет команду и ждёт ответ до таймаута. Использует `condition_variable` — механизм "разбуди меня когда придёт ответ"
- **`commandMtx_`** — мьютекс для командной очереди (только одна команда одновременно)
- **`eventCbMtx_`** — мьютекс для callback события (защита при установке нового callback)

**`healthCheck()`** — метод переподключения при потере связи. Вызывается из поллинг-потока. Реализует **экспоненциальный backoff**: при каждой неудаче следующая попытка через 5с, 10с, 20с, 40с (максимум 60с). Это стандартная практика для предотвращения flood reconnect.

Настройки UART (через `termios` — стандартный Linux API):
- CS8 — 8 бит данных
- CLOCAL | CREAD — включить приём
- без PARENB — нет бита чётности
- без CSTOPB — один стоп-бит
- IGNBRK — игнорировать break-сигналы

#### `hw/rfid/Rc522RfidProvider.hpp / .cpp` — Один RFID-считыватель

Реализует работу с чипом **MFRC522** через интерфейс **SPI** (Serial Peripheral Interface).

**SPI** — протокол для общения с периферийными чипами. Raspberry Pi и MFRC522 соединены 4 проводами: MOSI, MISO, SCK, CS. Работает быстрее UART, но требует большего числа проводников.

Что умеет MFRC522:
- Излучать 13.56 МГц радиосигнал
- Принимать отклик от RFID-метки
- Выдавать 4-байтный UID метки

Процедура чтения метки (через SPI):
1. `initializeChip()` — сброс и инициализация регистров чипа
2. Команда `REQA` (Request All) — запрос на все метки в поле
3. Если пришёл отклик (ATQA) — есть метка
4. Команда Anti-collision — получить UID метки
5. Проверка BCC (XOR всех байт UID) — целостность данных
6. Перевод UID в HEX-строку ("E201FC03")

**Файловый дескриптор** `fd_` — это число, через которое Linux предоставляет доступ к SPI-устройству как к файлу. `open("/dev/spidev0.0", ...)` → получаем fd, `ioctl(fd, SPI_IOC_MESSAGE, ...)` → отправляем SPI-транзакцию.

Два режима работы:
- `pollLoop()` — непрерывный опрос в фоновом потоке, вызывает callback при обнаружении метки
- `readOnce(timeoutMs)` — разовое чтение с таймаутом (для StartupService)

#### `hw/rfid/MultiRc522RfidProvider.hpp / .cpp` — Несколько RFID-считывателей

Обёртка над несколькими `Rc522RfidProvider` (до 6 устройств). При вызове `readAllOnce()` параллельно опрашивает все считыватели и возвращает список всех найденных меток.

Использует **std::future / std::async** — C++ механизм параллельного выполнения: запускаем несколько задач одновременно, потом ждём результатов всех. Это быстрее чем опрашивать по очереди.

#### `hw/rfid/MockRfidProvider.hpp / .cpp` — Заглушка RFID для тестов

Возвращает заранее заданные UID в заданном порядке. Позволяет тестировать логику мониторинга модулей без реального железа.

#### `hw/scanner/HidScannerProvider.hpp / .cpp` — USB HID сканер штрихкодов

Читает USB-сканер как **HID (Human Interface Device)** — то есть как клавиатуру. Большинство промышленных сканеров работают именно так: при сканировании они "печатают" цифры и нажимают Enter.

Использует Linux `evdev` API (`/dev/input/eventX`) для низкоуровневого чтения клавиш в обход графической системы (сканер работает даже если Qt не захватил фокус).

Таблица `keycodeToChar()` — перевод Linux keycodes в символы ASCII. Например:
- `KEY_1` ... `KEY_0` → цифры 1-0
- `KEY_Q` ... `KEY_P` → буквы верхнего ряда QWERTY
- `KEY_ENTER` → сигнал завершения штрихкода

#### `hw/scanner/SerialScannerProvider.hpp / .cpp` — Сканер через последовательный порт

Для сканеров, которые подключаются через RS-232/USB-Serial. Читает символы по одному, накапливает до `\n` или `\r`, потом вызывает callback.

Отличие от HID: сканер присылает текст, а не коды клавиш. Более простой парсинг, но нужна другая физическая конфигурация.

#### `hw/scanner/MockScannerProvider.hpp / .cpp` — Заглушка сканера для тестов

Позволяет программно "сканировать" штрихкод. Используется в интеграционных тестах.

#### `hw/stm32/MockStm32Link.hpp / .cpp` — Заглушка STM32 для тестов

Имитирует ответы STM32. Позволяет настроить что именно отвечать на `Ping`, `GetSwitchSnapshot` и т.д. Все тесты бизнес-логики работают через него.

#### `logging/SpdlogFileLogger.hpp / .cpp` — Логирование в файл

Реализует `IEventLogger` через библиотеку **spdlog**.

**spdlog** — C++ библиотека логирования. Выбрана потому что:
- Очень быстрая (асинхронная запись — не блокирует основной поток)
- Автоматическая ротация файлов по размеру (старые записи не занимают весь диск)
- Форматирование с временными метками и уровнями (INFO, WARN, ERROR)
- Заголовочный файл, не нужна сложная установка

#### `logging/SqliteEventLogger.hpp / .cpp` — Логирование в базу данных

Пишет события в таблицу `event_log` в SQLite. Это позволяет:
- Просматривать историю событий в веб-интерфейсе
- Фильтровать по уровню и коду прямо через SQL
- Хранить лог вместе с данными приложения

#### `logging/LoggerFactory.hpp / .cpp` — Фабрика логгеров

Создаёт нужный тип логгера на основе конфигурации. Можно логировать и в файл, и в БД одновременно через `CompositeLogger`.

#### `time/IClock.hpp / SteadyClock.hpp` — Абстракция времени

`IClock` — интерфейс для получения текущего времени. `SteadyClock` — реализация через `std::chrono::steady_clock`.

**Зачем нужна абстракция времени:** в тестах можно подставить "поддельные часы" и симулировать прошедшее время. Это позволяет тестировать таймауты и дебаунсинг без реального ожидания.

### `config/config.json` — Конфигурация системы

```json
{
  "log_file": "/opt/smartcart/shared/smartcart.log",
  "sqlite_path": "/opt/smartcart/shared/smartcart.db",
  "stm32_device": "/dev/ttyUSB0",
  "stm32_poll_ms": 500,
  "rfid_enabled": true,
  "rfid_spi_devices": ["/dev/spidev0.0", ...],
  "rfid_module_roles": {
    "E201FC03": "REEL",
    "E3906D2D": "FEEDER"
  },
  "switch_tracked_channels": [0, 1, 2, ...],
  "debounce_ms": 50,
  "slot_to_led_map": [0, 2, 4, ...]
}
```

Ключевые параметры:
- `stm32_device` — Linux-путь к UART STM32. В текущем конфиге используется `/dev/ttyUSB0`; для GPIO UART на Raspberry Pi часто используется `/dev/ttyAMA0`.
- `stm32_poll_ms: 500` — опрашивать STM32 каждые 500 миллисекунд
- `rfid_spi_devices` — список SPI-устройств. На RPi доступно до 6 SPI CS-пинов.
- `rfid_module_roles` — UID RFID-метки → тип модуля. Система узнаёт "это катушечный модуль" по UID.
- `debounce_ms: 50` — игнорировать изменения переключателя короче 50мс (дребезг контактов)
- `slot_to_led_map` — слот №1 → LED №0, слот №2 → LED №2, и т.д.

## Как всё работает вместе: полный сценарий

### Сценарий: оператор подбирает материалы для заказа

1. **Запуск** (`main_qt.cpp`): `AppBootstrap` собирает систему, `StartupService` согласует БД с физическим состоянием слотов. На экране появляется "Готов".

2. **Загрузка заказа** (`AdminView` → `OrderImportService`): Администратор открывает XLSX-файл BOM. `BomOrderImportService` распаковывает файл, читает XML, извлекает артикулы и количества. Создаются записи в таблицах `orders` и `order_items`. Workflow переходит в `ORDER_LOADED`.

3. **Начало подбора** (`WorkerView`): Оператор нажимает "Начать подбор". Workflow переходит в `PICKING_MATERIALS`.

4. **Сканирование катушки** (`AppStateMachine.scanBarcode()`):
   - Оператор сканирует штрихкод катушки
   - `Stm32PollingService.recordBarcodeScan()` ищет артикул в заказе
   - Находит позицию заказа с target_slot = 5
   - Создаёт `PendingScan` (ожидающий скан)
   - На экране появляется подсказка: "Положите в слот 5"

5. **Физическое размещение**:
   - STM32 через UART отправляет `EvtSwitchChanged` (channel=4, occupied=true)
   - `UartStm32Link.rxThread_` читает байты из UART-устройства, заданного в `config.json`
   - `StreamParser` собирает фрейм, проверяет CRC
   - `handleParsedFrame()` вызывает `eventCb_`
   - Callback попадает в `Stm32PollingService.handleEventFrame()`
   - `handleOccupiedSlot()` обнаруживает `PendingScan`, сверяет слот
   - Если слот правильный: `OrderRepositorySqlite.updateItemPlacement()` → status=Placed
   - `WorkflowService.notifyMaterialPlaced()` проверяет все позиции — если все Placed → переходит в `LOADING_FEEDERS`

6. **Подтверждение на экране** (`WorkflowDialogManager`): Появляется диалог "Все материалы подобраны. Загрузите питатели."

7. **Выдача на линию** (`WorkflowService`):
   - Оператор подтверждает каждую позицию: `markItemIssued(barcode)`
   - При полном выдаче: `completeIssuing()` → `ORDER_COMPLETED`

8. **Возврат остатков**: Неиспользованные катушки сканируются и возвращаются. `markLeftoverReturnedByBarcode()` → status=Returned.

9. **Завершение**: Workflow возвращается в `FREE`. Генерируется отчёт. БД содержит полную историю: что, когда, кто.

## Развёртывание на Raspberry Pi

Программа разворачивается на Raspberry Pi как основной systemd-сервис:
- `smartcart-ui.service` — Qt GUI (запускается при включении, показывает экран)

Структура на диске:
```
/opt/smartcart/
  current → releases/20260501-123456-abc123/   ← симлинк на текущую версию
  releases/
    20260501-123456-abc123/                     ← конкретная версия
      smart_cart_ui                             ← Qt бинарник
      smartcart_app                             ← CLI бинарник
      config/                                   ← конфигурация
      migrations/                               ← SQL-миграции
  shared/
    smartcart.db                                ← база данных (между обновлениями)
    smartcart.log                               ← логи (между обновлениями)
```

**Почему симлинк `current`:** при обновлении просто создаётся новая папка, и симлинк переключается. Если что-то пошло не так — один `ln -s` возвращает предыдущую версию.
